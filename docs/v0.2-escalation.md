# V0.2 首要里程碑：可控的模型自动升级

状态：设计约束及本地 `0.2.0.dev0` 实现基线。已实现三档初始策略、串行执行、固定验收、失败分类、一次受限升级和本地记录。真实工程已完成一次 Terra 首次成功；真实升级挽救效果尚未验证。使用方式与实际证据见 [v0.2-runtime.md](v0.2-runtime.md)。V0.1 的静态配置和 apply 行为保持兼容，plan 新增 initial_execution 建议字段。

目标：初始模型未通过任务验收时，先判断失败原因；只有证据支持、用户策略允许且预算满足时，才切换到指定的下一模型，再以相同标准验收并记录全部代价。第一版只做单任务串行闭环，多 Agent 通信和并发后置。

## 示例与证据边界

用户可以配置 Terra → Sol，或将 `balanced → reasoning` 映射到自己可用的模型。具体模型 ID、effort 和升级链属于配置；核心不得硬编码 Terra/Sol 或假定它们的相对价格和成功率。

“确认是模型能力问题”无法仅凭退出码或模型自述完成。初版把它定义为**满足明确证据条件的升级候选**，记录证据及剩余不确定性，不宣称已经证明因果关系。

升级候选须同时满足：

- 用户预先授权这次执行及自动升级，目标模型在允许列表内。
- 执行器和验证器正常，所需依赖与权限齐备，初始环境和既有失败已记录。
- 与当前任务相关的验收不通过，可复现，且不能归因于既有失败或基础设施错误。
- 若策略允许，已把验证反馈提供给同模型进行一次受限修正，结果仍不通过；策略也可明确禁用该修正。
- 没有取消或预算终止信号；剩余尝试、时间及可核验预算允许升级。

## 失败决策表

| 分类 | 证据示例 | 初版动作 |
|---|---|---|
| 认证或模型权限 | 明确的认证失败、模型访问拒绝 | 停止并报告；不升级 |
| 额度或限流 | 明确的额度/速率限制响应 | 记录并停止或按有限退避策略等待；不升级 |
| 网络或服务错误 | 连接失败、明确的服务端暂时错误 | 有限同模型重试；不升级 |
| 环境或执行器错误 | 缺依赖、sandbox 拒绝、执行器崩溃 | 停止并报告；不升级 |
| 验证器错误 | 验证命令不可运行、验证超时、结果格式无法解析 | 标记验证无效；不升级 |
| 任务质量失败候选 | 验证器正常、相关验收持续不通过，且基线未出现该失败 | 满足证据、授权及预算后允许一次升级 |
| 取消或预算终止 | 用户取消、到达运行上限 | 终止；不升级 |
| 未知 | 日志不足、只有非零退出码、相互矛盾的错误 | 停止自动升级，报告缺失证据 |

模型输出“完成”、进程退出 0 都不等于验收成功；进程非零也不等于能力不足。测试通过只证明已声明的验收通过，不代表代码完全正确。验证命令来自用户/项目的预先配置，不执行失败日志里临时出现的任意命令。

## 执行与预算

执行状态按 `planned → running → verifying → deciding → retrying/escalating → succeeded/failed/cancelled/budget_exceeded/needs_attention` 记录。只有模型完成和独立验证都符合预定标准，才能标记 succeeded。

建议初版缺省为自动升级关闭；启用后默认允许一次模型升级，最多三次模型尝试（首次、可选同模型修正、升级尝试）。基础设施重试另有明确次数上限，所有尝试都计入累计时间、Token 和费用，不能无限循环或静默继续升级到更高档模型。

预算区分：运行次数和墙钟超时可以由 ATR 控制；Token 或费用硬上限取决于宿主接口能否提供及时观测和限制。若只能在调用结束后拿到用量，只能禁止下一次调用并报告超出，不能承诺对当前调用精确截断。无法取得可靠费用上界时，不把估算值宣传成费用硬限制；要求硬限制的策略应拒绝不满足条件的执行。

升级前检查预算，执行中响应超时和取消，结束后累计实际可观测用量。账号可用性只能由宿主错误或实际调用反馈确认，目录识别不是权限证明。

## 项目状态与升级上下文

开始时记录项目基线和用户已有变更。每次尝试保留改动、验证输出和父尝试 ID。不得为了重试而丢弃用户的初始工作；工作目录已被外部修改、无法安全隔离尝试时停止自动重试。

Sol 等下一模型接收任务、约束、相关文件状态、上次修改摘要和结构化失败证据。记录其起点是原始快照还是上一尝试的候选修改，保证结果可追溯。初版不需要多 Agent 对话、独立 Reviewer 模型或多方消息总线。

## 记录与报告

每次尝试记录 run/task/attempt ID、parent_attempt_id、模型和 effort、策略版本、项目快照标识、开始/结束时间、退出状态、失败分类、验证结果及证据引用、是否升级和升级理由。

用量字段包含输入/输出 Token、缓存等宿主可观测项、延迟、费用数值/币种、实际或估算标记及价格来源日期。不可观测值为 null；Plus 不可见的额度消耗不换算成虚构金额。完整日志按项目本地存储，默认汇总报告引用证据而非复制可能敏感的原始上下文。

报告至少包含：

- 首次成功率：首次尝试验收通过任务数 / 已开始执行的任务数。
- 升级挽救率：升级后验收通过任务数 / 已发起升级的任务数，同时显示未完成升级数量。
- 端到端成功率：最终验收通过任务数 / 已开始执行的任务数，同时分列运行中、取消、环境失败和未知原因，不能通过隐藏这些任务抬高成功率。
- 每个任务的累计 Token、累计可观测费用和总延迟，以及升级阶段增加的代价。部分费用缺失时，显示已知小计和缺失情况，不能当成完整总成本。

不同任务和模型的原始成功率不直接证明升级有效。后续用相同任务/基线比较 Terra-only、Sol-only 和受控升级策略，报告同模型修正的贡献及额外验证开销。

## 实施顺序与验收

1. 实现一次串行执行、基线采集、独立验证、取消和完整 attempt 记录；先使用假执行器。
2. 实现失败分类器与纯策略决策函数，输出动作、理由、证据引用和预算状态。
3. 接通一次受限升级与上下文交接，持久化状态，恢复时不得重复启动已完成尝试。
4. 汇总用量和三项成功率，输出可审计的每次尝试与升级成本。

必须覆盖的验收：验证失败后升级成功；同模型修正成功后不再升级；升级仍失败后终止；认证/额度/网络/环境/未知原因都不触发升级；取消和预算不足阻止升级；初始已有失败不被误归因；缺失费用保留 null；用户变更不丢失；恢复不重复调用；失败和中断样本仍出现在报告中。

上述模拟验收通过后，再使用小型真实任务开展有限验证，分别报告配置正确性、模型访问权限和策略效果，不把其中一项当作其他项的证明。
