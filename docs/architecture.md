# ATR V0.1 架构与后续计划

## 已实现的边界

`core.py` 的 Model / Role / Profile / Assignment / Plan 不包含 Codex 字段，也不导入适配器。Task Analyzer 用确定性中英关键词判断 category、complexity、risk；Policy 根据 Profile、复杂度和风险决定档位与审查角色。Model Router 在用户映射的模型中选择目标档位或最接近的可用档位，解释降级。默认替换不支持的推理强度；显式覆写不合法强度则报错。

`profiles.py` 用同一结构定义五种团队，覆盖并发、角色启用、档位、模型、强度与指令。并发计数仅针对子 Agent。`code-review` 固定只读属性，宿主的现有权限不在 ATR 控制范围内。

`config.py` 管理模型注册数据和初始化。模型示例名称仅存在于 Codex 适配层数据中，可由 `--model-map` 和用户配置替代。catalog 是支持强度的静态证据，绝不等价于账号访问证明。

`adapters` 暴露最小协议，只有 Codex 实现。其职责是本机命令探测、原生 TOML 与 AGENTS.md 渲染、原生字段验证。未来平台可使用自己的格式和能力矩阵，不能直接照搬 Codex 角色/模型切换语义。

`service.py` 组合配置、静态团队、适配器与安全文件层。`storage.py` 只理解文件快照、哈希、差异和事务。`cli.py` 使用 argparse，不存在隐藏模型调用。Skill 仅作为 CLI 入口分发，不复制路由程序。

V0.2 开发版增加 `task_policy.py` 的三档初始模型选择，以及 `runtime/` 的任务契约、快照、执行进程、Codex 事件解析、纯升级策略和原子 JSON 运行记录。只有 `run --execute` 调用模型；其他配置与规划入口不发起推理。初版串行单写者使用本地 JSON，不依赖 SQLite；未来多任务查询需求出现后再评估迁移。

## 文件事务

1. 解析现有配置、检查路径与当前托管哈希，生成全部目标内容。
2. 在临时 CODEX_HOME 中严格验证每个新角色层和主配置，不修改项目。
3. dry-run 输出 diff 并结束。apply 获取项目锁，重新检查快照与状态。
4. 修改前保存全部相关原始字节、修改后哈希及上一版本状态，写入 prepared journal。
5. 逐文件原子替换，状态文件最后提交；成功删除 journal。普通异常恢复快照。
6. 崩溃后 recover 拒绝事务之外的修改，恢复全部旧内容。rollback 先校验当前哈希，再执行相同文件批次恢复。

并发假设：锁协调 ATR 实例；不协调外部编辑器，提交期间不要修改目标文件。不是跨文件系统原子事务或数据库。只要一个托管文件人工变化，就整体拒绝 apply/rollback；这比自动猜测人工变更意图更保守。备份、journal 与 state 不应被手动改写或提交。

## V0.2：优先实现可控的模型自动升级

首个可交付闭环是：初始模型执行 → 独立验证 → 分类失败 → 按策略决定是否升级 → 使用允许列表内的下一模型执行 → 再验证 → 记录完整成本和结果。Terra → Sol 是用户可配置的示例链，不作为核心硬编码，也不预设升级一定更有效。

1. **最小串行执行与验证**：核验当前 Codex 执行接口，实现 `Executor` 和 `Verifier`。只处理一个任务，先支持 dry-run、权限、超时、取消、项目基线检查和执行记录，不引入团队通信或 DAG。
2. **失败分类与升级决策**：优先区分认证/权限、额度、网络、环境、验证器错误与可复现的任务质量失败。未知原因停止自动升级。先通过规则和验证证据判断，避免额外 LLM 诊断成为默认开销；不把退出码或一次测试失败直接解释为模型能力不足。
3. **有界升级执行**：用户明确启用升级并指定链、重试次数和预算；初版至多一次同模型反馈修正、一次模型升级，不循环。保留原始项目状态和尝试谱系，给下一模型传递任务约束、失败证据和必要修改摘要。升级后仍由同一验证标准判断成功。
4. **成本与成功率报告**：逐次记录模型、effort、Token、延迟、费用来源、失败分类、升级理由及验证结果；报告首次成功率、升级挽救率和端到端成功率。费用或额度不可观测时留空，不能伪造 Plus 额度开销。先用假执行器完成分类/预算/恢复测试，再对小型真实任务做受控评测。

完成标准：可复现一次“任务质量验证失败 → 获准升级 → 验证通过”的完整记录；所有非能力类错误和未知原因均不能触发模型升级；明确记录失败与升级的累计代价。详细决策表与验收案例见 [v0.2-escalation.md](v0.2-escalation.md)。

多 Agent 通信、依赖 DAG、并发调度和共享文件协调排在该闭环之后，不是 V0.2 首个里程碑的前置要求。

## V1.0：数据驱动路由，分四个增量

1. 发布可授权使用的任务清单、环境镜像/锁文件、固定 commit、验证命令与输入哈希。任务按类型、难度和风险分层；当前 `evals/routing_cases.json` 仅做规则回归，不能代表模型质量。
2. 建立 `evals/result.schema.json` 格式的 JSONL 结果：明确模型版本、effort、重复次数、输入输出 Token、实际/估算费用来源、首响应及总延迟、失败与升级成本。无法观测的字段留 null，不能编造 Plus 订阅内部成本。
3. 比较单模型、静态团队与受控动态路由，在固定预算/重复次数下报告成功率、总费用、延迟分布和区间估计；保留失败样例。将策略选择集和最终评估集分开，防止在测试任务上调参。
4. 在足够数据覆盖后学习分层策略；保留规则回退、冷启动和最小样本要求。新策略先 shadow 比较，经过回归门槛再切换，支持恢复到已知策略版本。

完成标准：任意公开结果能追溯到任务、环境、策略和每次调用；相同数据能复算报告；收益不依赖主观模型排名。
